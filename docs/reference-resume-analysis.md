## 2. 共同核心 = 行业基线

四份样本的共同技术点，恰好就是本项目 W1–W4 的全部内容：

- RS485 + **UART DMA/空闲中断判帧**（R3 明写，其余隐含）
- Modbus RTU 主站或从站、**保持寄存器映射**、CRC16、响应超时与异常码处理
- RTOS 多任务：通信线程独占串口、消息队列/邮箱解耦、避免多任务竞争串口资源
- 可配置设备表/点表（R1、R2、R3 都有"寄存器映射"条目）

**结论：W1–W4 计划没有遗漏，做完全部内容即达到行业基线；无需为对标增删范围。**

## 4. 我们有、四份样本都没有的（差异化重点）

1. **Linux C 服务端**：epoll 事件循环 + 自定义帧协议（拆包/粘包/心跳）+ SQLite 入库（变化触发 + 1s 下限 + 保留期）。四份样本全部止步于 MCU 或云平台 SDK，无一人自写 Linux 服务端——这是对"嵌入式+Linux"岗位的最大差异点。
2. **故障注入 + 系统化测试**：6 种故障模式、1000 次连读、24h 稳定性、测试报告。样本中只有 R2 给了量化成效，无人做系统性故障测试。
3. **链路三层全自研**：F103 从站、F407 主站、Linux 服务端每层都能讲源码；样本要么只有主站（依赖现场设备），要么双端但无服务端。
4. **寄存器表单一来源**：CSV + 生成器产出 C/Python/文档，改一处全同步。工程化亮点，一句话就能讲清。

## 5. 可复用的简历写法（学结构，不抄内容）

- **量化成效必须实测**：R2 写"定位误差 ±0.05mm、调节 0.5s""省 80% 人工、升级 5 分钟"。我们对应的实测数字：1000 次连读错误数、超时/重试统计、离线恢复时间、24h 无复位、日入库行数。**W1 起每项验收都记录实测值，没有数字的条目不写。**
- **高频关键词**（按面试官检索习惯）："DMA+串口空闲中断""保持寄存器映射""响应超时与异常码""消息队列避免资源竞争""状态机"。
- **条目结构**：底层适配 → 协议栈/任务设计 → 业务逻辑 → 联调验证，与 W1→W6 顺序一致。
- **竞争节奏**：R1（同为 2027 届）2026.01–03 完成同构网关，样本普遍有 2 段项目。我们 12 月开工、1 月底出 MVP，数量不占优——拼深度（Linux + 测试体系）而不是拼条目数；已有 CAN/UDS/OTA 背景补足广度。

## 6. 面试题库（从样本条目反推）

| 面试官会问 | 我们的答案锚点 |
|---|---|
| 多任务怎么避免 RS485 总线竞争？ | 单事务状态机 + 请求队列，一次只允许一个事务，比"互斥锁包串口"更进一步 |
| 多字节序/数据类型怎么处理？ | uint32 统一大端 ABCD、偶数对齐；点级镜像一次性更新 32 位，避免半新半旧 |
| 从站不响应怎么办？ | 50ms 超时（约 10 倍帧时间）、retry_max=2、连续 3 次离线、降频轮询、连续 2 次成功恢复 |
| 怎么证明它稳定？ | 故障注入 6 模式 + 1000 次连读 + 24h 实测数字，全部有测试报告 |
| 为什么响应要及时关方向？ | DMA 完成 ≠ 发送完成，必须等 UART TC 再拉低 DE，否则截断最后一字节 |
